## Domain 1: Zynq/ZedBoard Camera Pipeline

You maintain the OV7670 → AXI VDMA → DDR capture pipeline (`fpga/camera_i2c/`, `fpga/zynq_camera_sys/`) and the bare-metal PS (ARM Cortex-A9) app (`fpga/vitis/src/main.c`) meant to stream frames to a host PC over raw UDP. **Not yet fully working**: basic UDP (ping-level) has been established, but an actual end-to-end camera→FPGA→UDP→laptop video stream has not been formulated — `main.c` doesn't even call `init_vdma()` currently (commented out for a ping test). ## Domain 2: Digital↔Optical Interface Bridge (blocked)

The photonic computing arm runs the **same class of large VLA model as the Jetson arm**, on a confirmed end-to-end photonic execution platform. Intended pipeline: (1) FPGA samples the camera, (2) FPGA electro-optically encodes the signal for the photonic network's input, (3) FPGA reads the photonic network's output back, (4) FPGA converts that to motor angles/STEP-DIR. **Still blocked**: no interface spec exists for steps 2/3 — no datasheet, no confirmed device, no signal-level detail. Do not fabricate a protocol and write Verilog against it. Two things to flag if assigned this: (a) since the model is VLA-scale, its output is expected to be `theta_a/b/c` angles, not raw step counts — step 4 needs the same `angle_to_steps()` conversion already used in `firmware/stm32_ml_control_and_vision/BallBalancingBot/MotorControl.h`, not a from-scratch one; (b) carrying camera-frame-scale data across this bridge is comparable in scale/risk to the still-unresolved Domain 1 problem — don't assume it's easier. First deliverable if picked up: a written architecture sketch of known/unknown, not RTL.

## Domain 3: Vision Model → FPGA Weight Compilation (PAUSED — not the current priority, kept as reference)

`SharedVisionBackbone` (64,260 params, `train_cnn_2d_tracker_marker.py`) has no FPGA-targeted export path; this domain was building one pre-pivot. Don't resume by default — check with the user first.

- **Weight storage is not the bottleneck** (~125KB at 16-bit, well inside 612.5KB). **Activation buffering is**: the first encoder layer's 128×128×16 feature map costs ~512KB whole-frame at 16-bit — near the entire budget alone. Design a streaming, line-buffered dataflow (row buffers per conv layer), not whole-frame on-chip arrays.
- `nn.GELU()` (10 activation sites) has no native HLS/fixed-point form. **Decided (2026-08-11, empirical): keep GELU** — ReLU lost ~16% relative ball-position accuracy and showed severe seed-to-seed dying-unit instability in this architecture's narrow channel layers. Custom GELU LUT already built and verified: `fpga/hls4ml_custom_layers/gelu_lut.py`.
- **`ConvTranspose2d` vs `Upsample+Conv2d`: DECIDED 2026-08-13, `Upsample+Conv2d` wins** — a 30-run reweighting sweep showed the ball-tracking instability originally blamed on the decoder choice was actually shared-encoder gradient competition (fixed by reducing mask/heatmap loss weights to ~0.1/0.02); at that setting `Upsample+Conv2d` matches `ConvTranspose2d` on ball tracking while beating it on mask quality at every weight setting tested. Cost: +42% decoder params (91,140 vs 64,260), still inside budget. With this decided, **every layer type is hls4ml-native except GELU** (already solved) — no further custom-layer engineering needed once `ml_vision` ships this architecture into production.
- Fold `BatchNorm2d` into the preceding conv's weights/bias at export time — never a separate runtime op on-chip. Drop the decoder heads' `F.interpolate(...)` calls — a no-op given the locked 128×128 input.
- Build a weight compiler under `fpga/` consuming the `.pt`/`.onnx` export, emitting `ap_fixed<W,I>` arrays. Read `host_software/ml_audio/export_audio_weights.py`'s `--hls` mode for the established pattern first — don't modify it, it's outside your directory.
- **First fixed-point trial's numbers are invalidated, not decided** — they ran against a since-corrected-checkpoint-bug. Re-run `trial_fixed_point_quantization.py` with calibrated per-layer `int_bits` from real observed ranges once a corrected checkpoint exists, per the `model-iteration-constraints` skill's calibration guidance.
- Read `fpga/hls4ml_custom_layers/README.md` before touching this area — documents the isolated `vri_fpga_hls4ml` conda env, real gotchas already hit, and that C-simulation doesn't run natively on Windows (still open — likely needs WSL/Linux).

## Domain 4: PID + Inverse Kinematics Control Core (live priority, unblocked)

`fpga/hls_hardware/PIDControllers.cpp` + `InverseKinematics.h` already implement the control law (X/Y PID → tilt angle → 3-motor delta-robot IK) as synthesizable HLS C++ (`ap_fixed<32,16>`), not yet wired into `fpga/vitis/src/main.c` (which currently only attempts camera+UDP — itself unfinished, see Domain 1). Start with a **digital testbench for `balance_controller()`** (known coords in, verified angles out) — needs no physical hardware, no optical spec, no vision checkpoint, unblocked regardless of anything else here.

**"Option B" (in progress, not yet built):** route motor control through the FPGA directly (STEP/DIR generation in hardware), eliminating the STM32 hop for the Jetson/expert arm. `fpga/main_controller/stepper_motor_controller.v` already does this (written for Opal Kelly, but the core module itself has zero Opal Kelly dependencies — only the wrapper does). Precedent for the porting work: `fpga/camera_i2c/ov7670_axi_stream.v` was packaged as custom Vivado IP and wired into `fpga/zynq_camera_sys/camera_system.bd` — same process applies here but with an **AXI4-Lite** interface (register read/write), not `ov7670_axi_stream`'s AXI4-Stream. RL control-net output is already step-space (needs zero conversion into `target_position`); VLA-style models output `theta_a/b/c` and need `angle_to_steps()` first. **Open, unvalidated**: `stepper_motor_controller.v` is proportional-only with a hard-clamped ~2kHz max step rate — cruder than `AccelStepper`'s trapezoidal profile currently on the STM32; it moved real motors before, but smoothness parity with the current solution is unverified.
