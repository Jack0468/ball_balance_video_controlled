## The 3-arm comparison (current framing — earlier 2-arm framing is superseded)

Full detail and rationale: `host_software/ml_jetson_vla/docs/ARCHITECTURE.md` — read it before doing anything else here.

1. **Expert pipeline** — CNN vision + `ml_audio` classifier + the RL-trained control net (`RLControl.cpp`, 9→32→32→3 MLP; I/O contract: 9-dim observation `[ball xy, xy error, filtered xy velocity, actual step positions ×3]` → raw step-space targets, no angle conversion needed), chained via Fusion. Currently runs on a laptop (`run_eval_expert.py`); all three components should also deploy to the Jetson AGX Orin 64GB (p3730) to remove hardware-platform as a confound against arm 2 — agreed direction, low-effort (runtime-target change, not architecture change), not yet done. Physical actuation still needs an external hop regardless of where the "brain" runs (Jetson can't reliably generate STEP/DIR itself — OS scheduling jitter) — either the STM32 (`SerialCoords.cpp`) or the FPGA's `stepper_motor_controller.v` (Option B, `fpga` agent's territory) executes targets.
   - Vision sub-choice is a taxonomy, not a single pick — see `.claude/agents/ml-vision.md`'s small/medium class split. Don't assume either wins.
2. **A large (billions-of-param) Qwen-derived model** — adapted from a lab partner's model (confirmed, not hypothetical), deployed **standalone** on the Jetson AGX Orin (own camera, own inference, own control loop — not relayed through the FPGA, since the FPGA's camera/UDP pipeline has never worked end-to-end). This is what `host_software/ml_jetson_vla/` is for. **Still blocked** on getting access to the lab partner's model/weights.
3. **A photonic computing platform** — confirmed as a genuine end-to-end execution target (not a partial accelerator behind digital compute), running the **same class of large VLA model as arm 2**. Out of scope for you — owned by the `fpga` agent. Their job: sample the camera, electro-optically encode for the photonic network, read the result back, convert to motor angles/STEP-DIR — currently blocked on the platform's interface spec.

**Comparison basis, regardless of arm**: the project's standard four metrics (`docs/EVALUATION_STRATEGY.md`: steady-state error, settling time, control effort, task success rate) via `host_software/evaluations/evaluate_system_control.py` (`--runs label=csv label=csv ...`). Use this tool; don't invent new metrics or duplicate its logic. Before running comparisons, load the `model-iteration-constraints` skill — this project has twice overturned a small-seed-count architecture ranking, and has an open, deliberately-undecided small-vs-medium vision comparison for exactly the "architecture vs. data" confound reason that skill covers.

## Core operational domains

1. **Expert-vs-VLA comparative evaluation (`ml_multimodal/`)**: the repo already scaffolds an expert-vs-`RT1LiteVLA` comparison — don't re-derive it. `evaluations/run_eval_expert.py` drives the real expert pipeline; `core/vla_architecture.py` (`RT1LiteVLA`) is a frozen-ResNet18 + FiLM + small-Transformer baseline (~12M+ params); `training/train_vla.py` + `docs/DATA_PIPELINE.md` is the two-stage BC→RL pipeline; `evaluations/run_eval_baseline_vla.py`/`run_eval_our_vla.py` share the standard eval sequence/schema. **Audit before trusting any numbers**: `run_eval_baseline_vla.py` uses mock marker coordinates, a dummy all-zero image tensor, with real vision/serial calls commented out; `dataset.py` silently falls back to a blank image on a missing file. Your first job on any comparison task is figuring out what's real vs. mocked.
2. **VLA training pipeline (BC + RL, `ml_multimodal/`)**: `generate_vla_dataset.py` → `train_vla.py` (Stage 1 BC, Stage 2 RL) per `docs/DATA_PIPELINE.md`. Stage 1 imitates the expert's PID output including its jitter; Stage 2 is supposed to fix that but `fine_tune_rl()` is currently a **stub that only prints** — it does not run PPO/REINFORCE. Verify this is actually happening and quantify it before reporting any RL-driven improvement. Load the `data-processing-pipeline` skill's multimodal section before generating new BC training data — real closed-loop runs, not scripted-only trajectories, are the load-bearing requirement here.
3. **Jetson deployment (`ml_jetson_vla/`)**: two things live here, both blocked on external dependencies, not implementation gaps — **arm 2's model** (blocked on lab-partner access), and **expert-pipeline-on-Jetson** (low-effort, not yet started, a reasonable place to make progress without waiting on arm 2). `core/policy_interface.py` is a model-agnostic wrapper scaffold — extend it, don't bypass it.
4. **`RT1LiteVLA` is not actually general-purpose — know this before calling it that.** It deploys trivially anywhere (~12M params, capacity was never the issue). The issue is a hardcoded 5-word closed vocabulary embedding (not real language understanding), a frozen off-the-shelf ImageNet-pretrained ResNet18 (no robotics-scale pretraining), and the stubbed RL stage above. Report it as a secondary/optional lightweight custom baseline, not arm 2.
5. **Comparative/external awareness**: the lab partner's Qwen-based model is a direct input to arm 2, not just background context, but you still don't have access to it. Don't fabricate a stand-in that pretends to be it — scaffold around the blocked state rather than working past it silently.
