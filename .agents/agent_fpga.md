2. Vision Model → FPGA Weight Compilation & Inference Core (Phase A — first priority): The shared vision backbone (`SharedVisionBackbone`, 64,260 params exactly, defined and trained in `host_software/ml_vision/training/train_cnn_2d_tracker_marker.py`, evaluated in `host_software/ml_vision/evaluations/evaluate_shared_vision_backbone.py`) has no FPGA-targeted export path yet, and its inference-side hardware architecture is unresolved — this is the concrete gap you need to close. A feasibility pass (2026-08-11, full detail in `docs/plans/ml_system_parameter_budget.md` §5) already surfaced hard constraints you must design around, not discover the hard way:
   * **Weight storage is not the bottleneck** (~125KB at 16-bit for all 64,260 weights, comfortably inside the 612.5KB BRAM budget). **Activation buffering is the bottleneck**: the first encoder layer alone (`Conv2d(3,16,3x3)`, before the first `MaxPool2d`) produces a 128×128×16 feature map that costs ~512KB whole-frame at 16-bit — close to the entire BRAM budget by itself. You must design a streaming, line-buffered dataflow architecture (row-buffers per conv layer, in the Xilinx Vitis Vision Library pattern), not translate PyTorch layers into whole-frame on-chip arrays.
   * `nn.GELU()` appears at 10 activation sites and has no native HLS/fixed-point implementation (it needs `erf()`). **Decided (2026-08-11, empirical trial — see `docs/plans/ml_system_parameter_budget.md` §5.3): keep GELU.** ReLU was tested and rejected — it lost ~16% relative accuracy on ball-position error (32.2±0.1px vs. 37.3±6.6px) and showed severe seed-to-seed instability from dying units in this architecture's narrow 16/32/64-channel layers. Your job is to implement a lookup-table or piecewise-linear approximation of GELU on-chip — do not substitute plain ReLU as a "free" simplification, that option is already tested and closed. If the approximation proves too resource-costly during HLS design, raise leaky-ReLU as a fallback with the Electrical Engineer rather than silently falling back to plain ReLU.
   * Fold `BatchNorm2d` into the preceding conv's weights/bias at export time (standard technique, precomputable from `gamma/beta/running_mean/running_var`) — do not implement BatchNorm as a separate runtime op on-chip.
   * The decoder heads' `F.interpolate(..., size=(128,128), mode="bilinear")` calls are a mathematical no-op given the locked 128×128 input (three stride-2 `ConvTranspose2d` layers already take 16→32→64→128 exactly) — drop this from the FPGA implementation rather than synthesizing bilinear resize.
   * The `ConvTranspose2d(kernel=2, stride=2)` decoder layers are the cheap, non-overlapping special case of transposed convolution — no architecture change needed there.
   * DSP-slice usage and pipeline throughput against the 120Hz/<8.3ms budget are still open — that requires an actual Vitis HLS C-synthesis resource report once a first-pass streaming implementation exists, not hand estimation.

   Build a weight compiler, living under `fpga/`, that consumes the `.pt` state_dict or `.onnx` export the training script already produces and emits fixed-point (`ap_fixed<W,I>`, per `docs/HLS_DATA_TYPES.md`'s reasoning) weight arrays in the layout your streaming inference core needs. The closest existing precedent in this repo is `host_software/ml_audio/export_audio_weights.py`'s `--hls` mode (Keras model → C header with shape macros) — read it for the pattern, do not modify it, it is outside your directory. Note: a generator script (`export_weights.py`) referenced in the header comment of `ml_control`'s `weights.h` is missing from the repo — you do not need to recover it; it produced the STM32 control-net MLP's weights, a separate thing from both the vision backbone and the PID/IK control law below.

   Findings and a concrete implementation plan from a 2026-08-12 research pass (full detail and sources in `docs/plans/ml_system_parameter_budget.md` §5.7-5.9 — read those before starting this work, do not re-derive from scratch):
   * **The first fixed-point trial's numbers are invalidated, not decided.** `ap_fixed<16,6>` and `ap_fixed<12,4>` looked free (within noise of float32) and `ap_fixed<8,2>` collapsed (39px vs. 4.4px baseline) against `shared_vision_backbone_v1`, but that checkpoint was later found to have a bug in the model/training pipeline. Re-run `host_software/ml_vision/experiments/trial_fixed_point_quantization.py` once a corrected, retrained checkpoint exists — using calibrated, per-layer `int_bits` derived from real observed ranges, not the guessed blanket configs from the first pass — before acting on any bit-width choice. The 8-bit collapse has the signature of range-saturation from too few integer bits (the standard failure mode of un-calibrated quantization), not necessarily proof 8-bit is infeasible.
   * **hls4ml is a real partial accelerant, confirmed from its actual converter source, not a free ride.** `Conv2d`, `BatchNorm2d`, `MaxPool2d`, `Linear`, and `Upsample` are natively supported; `GELU`, `ConvTranspose2d`, and `AdaptiveAvgPool2d` are not. GELU is the hard blocker (it follows every layer, including the otherwise-native encoder) and needs a custom Extension API layer regardless of any other choice — a bounded, documented effort (~15 lines of core HLS for a simple elementwise op, per hls4ml's own example), not open-ended research. `AdaptiveAvgPool2d((1,1))` has a free exact fix: swap to `AvgPool2d(16)` given the locked 128×128 input. `ConvTranspose2d` may not need custom-layer work at all — hls4ml natively supports `Upsample`, and `Upsample + Conv2d` ("resize-convolution") is a standard alternative to transposed convolution — but that changes the trained model, so it needs an empirical accuracy trial (same methodology as the GELU/ReLU decision), not a silent swap.
   * **Follow the ordered plan in §5.9.** Steps 1-2 are done (2026-08-12), with real verified results, not just a plan: the `AvgPool2d(16)` pooling swap (`fpga/hls4ml_custom_layers/fpga_target_architecture.py`, numerically confirmed exact, diff ~7e-9) and the custom GELU hls4ml layer (`fpga/hls4ml_custom_layers/gelu_lut.py`, confirmed accepted by a real `hls4ml.converters.convert_from_pytorch_model` run — see the model graph log in `test_gelu_lut_conversion.py`'s output). Read `fpga/hls4ml_custom_layers/README.md` before touching this area — it documents the isolated `vri_fpga_hls4ml` conda env (deliberately kept separate from `ball_balance_env`), the gotchas already hit (`InputShape` must be a list-of-shapes), and that C-simulation doesn't run natively on Windows (a real, still-open environment question — likely needs WSL or Linux, not solved yet).
