### Marker Target Jump-Gate: `state_machine.py`'s Averaging Had No Outlier Rejection, Fixed With a Static-Position Model (Not a PredictionGate Port)

- **Bug, already confirmed real before this entry**: `TargetStateMachine.get_target_coords()` arithmetic-averaged `marker_history[color]` (a plain `deque(maxlen=10)` fed by `update_markers()` with whatever `{color: (x, y)}` the marker classifier reported that frame) with zero jump/outlier rejection -- unlike `PredictionGate` (`main_onnx_shared_vision_audio.py`), which already gates the ball's own position with an EMA/Kalman anchor, a jump threshold, consecutive-jump rejection, and a seed window. `evaluate_system_control.py`'s own `MIN_TRIAL_DURATION_MS` comment (shipped earlier the same day) already documents the symptom this causes: a sustained ~0.5-1s marker-classifier misclassification burst (this session's earlier yellow/green boundary-flicker findings) rides straight through the average and reaches 29.6mm on real data -- large enough to be mistaken for a genuine command transition.
- **Why this is a new design, not a copy of `PredictionGate`**: the ball genuinely moves and can be lost/reacquired elsewhere, which is why `PredictionGate` needs a motion model (EMA or Kalman) and an `AWAITING_BALL`/lost-and-reseed escape valve. A color marker is a static physical object glued to the printed sheet for the life of one session -- `docs/EVALUATION_STRATEGY.md`'s 2026-09-15 update confirms marker positions are only movable *between* setups, by hand, never mid-recording. So the right model is simpler: the current smoothed estimate is the best guess of a fixed true value; anything far from it is noise, reject it outright (don't blend it in, don't count it toward a "lost" reset), and let more accepted samples only sharpen the estimate. Implemented as `_MarkerPositionFilter` in `host_software/src/state_machine.py`, one independent instance per color (blue/green/red/yellow/black), replacing `marker_history`'s plain deque:
  - No velocity/Kalman term -- there is nothing moving to model.
  - No "lost"/reseed escape valve -- a burst of rejected candidates is not evidence the marker moved, so the anchor holds through the *entire* burst (this is the actual fix: with the old plain mean, a burst lasting >= the window size (10 samples) could fully replace the window and swing the average by close to the raw jump distance; the new gate rejects the burst's first sample against the pre-burst anchor and never updates, so every subsequent sample in the same burst is rejected too, not just the first one).
  - A color going undetected for a while (occlusion, ball sitting on the marker, a transient classifier miss) simply isn't fed an `update()` call that frame -- not gated, not decayed, not reset. The estimate holds at its last accepted value indefinitely, which is correct precisely because the true position hasn't changed.
  - A `seed_window`/`seed_consistency_mm` phase (5 mutually-consistent detections within 10mm before the estimate is trusted at all, mirroring `PredictionGate`'s seed rationale) protects against a noisy first-ever detection for a color. `jump_threshold_mm=15.0` sits between normal same-marker jitter (a few mm, comparable to the ball's own ~5.6mm mean error) and the sheet's real 30mm inter-marker spacing (derived from `aruco_markers_03_manifest.json`'s `center_mm` via the standard `touch_x = W/2 - manifest_x`, `touch_y = manifest_y - H/2` convention), so a same-marker reading is accepted and a different-marker misclassification is rejected.
  - Synthetic smoke test before touching real data: seeded green at (0, 30), then fed 20 consecutive frames at yellow's real position (-30, 0) (exactly the yellow-flickers-to-green failure shape) -- target stayed at (0.1, 29.9) throughout, unmoved; a legitimate small-jitter update immediately afterward was still accepted normally. The old plain-mean code, fed the same 20-frame burst, would have fully replaced its 10-slot window and reported essentially (-30, 0) -- a ~42mm error instead of ~0.
- **Validated against the three real CSVs named in the bug report** (`ground_truth_jetson_20260915_{150041,150729,151627}.csv`), via a new script, `host_software/ml_vision/experiments/marker_target_jump_gate_eval.py` (comparison report, not a fixed benchmark, per this project's `experiments/` convention -- none of the existing `experiments/` scripts covered this). **Real limitation stated plainly**: these recordings log `get_target_coords()`'s OLD, already-averaged OUTPUT every frame, not the raw per-color detections that fed it -- no raw per-color log exists for these runs, so a byte-for-byte replay of the new gate (which runs pre-average, on raw candidates) isn't possible against this data. The script instead identifies each recording's real go_green/go_yellow/go_red/go_black dwell phases (merged segments matched against the sheet's known touch-mm marker positions -- green (0,30), yellow (-30,0), red (30,0), black (0,0); black is disambiguated from the coincident (0,0) "center" default by requiring it to occur after at least one green/yellow/red phase, since a real `go_black` necessarily follows those in the Standardized Evaluation Sequence) and replays each phase's recorded trajectory through a fresh `_MarkerPositionFilter(history_size=10)` (matching `TargetStateMachine`'s actual default exactly) as the closest available proxy, comparing frame-to-frame step-size stats before/after.
  - **Real numbers**: across the 3 recordings' 18 total labeled marker-following phases, max single-frame step dropped by 79-96% in every phase that wasn't a cold-start (e.g. file `150041` go_black: 1.1mm -> 0.2mm; file `150729` go_red: 0.5mm -> 0.1mm; file `151627` go_yellow: 0.7mm -> 0.1mm; file `150729` go_yellow: 0.5mm -> 0.1mm). No phase's max step got worse.
  - **The two 29.6mm spikes reported in `evaluate_system_control.py`'s own comment were reproduced exactly** (file `150729` rows 0:112, file `151627` rows 0:141) and showed 0% reduction in this specific harness -- investigated rather than left unexplained: both land within the first 5 frames of that recording's green history (i.e. the color's very first-ever detection that session), during the seed window. This is not a gap in the fix; it is the harness's own stated limitation cutting the other way here: the OLD code (being replayed as the "before" signal) had zero minimum-sample requirement and returned a single raw detection immediately as the target, which is the actual mechanism behind a wrong first-ever reading snapping the target hard on frame 1 -- exactly what these two spikes are. The NEW code cannot reproduce this failure at all: `get_target_coords()` returns the `center` fallback (0, 0) for any color with no confirmed `_MarkerPositionFilter.position` yet (`filt.position is None`), never a single unvetted raw sample, so a bad first detection is invisible to the state machine until 5 mutually-consistent readings confirm it. ### Ground-Truth Telemetry: Throughput Collapse Diagnosed and Fixed
- **Symptom**: with `TouchTelemetryLogger` (ground-truth CSV logging, wired up 18/08) enabled, the bot lost control of the ball entirely. With `--log-csv off`, control returned to the same mild-oscillation baseline seen before any of the telemetry work -- i.e. the underlying, still-unsolved oscillation problem from 18/08 was untouched either way; the CSV logger was an independent, much more severe *additional* failure mode layered on top of it.
- **Root cause, confirmed from real recorded telemetry, not assumed**: the vision loop's sustained throughput collapses from the benchmarked ~95-107 FPS (no logger) to a median ~20-25 FPS with the logger active -- confirmed by computing inter-send gaps from `host_send_ts` across three real recordings (`host_software/data/01_bronze/evaluation/ground_truth_*.csv`), after first catching and correcting a measurement bug of my own (naively using row-count/total-time as "FPS" measures the firmware's 60Hz `TouchProbe` echo cadence, not the vision send rate -- each echo repeats whatever vision frame the firmware last received whenever vision is slower than 60Hz, so raw row timestamps are heavily duplicated). The on-screen status line's own FPS number was misleadingly showing 80-110 throughout, because it only times work *after* frame capture -- any stall further upstream (camera read, serial I/O) is invisible to it.
- **Suspected mechanism**: the original design had the main thread call `ser.write()` directly while a separate background thread read from the same `pyserial.Serial` handle -- either GIL contention between the two threads' Python-level work, or contention at the OS/driver level from two threads touching one handle concurrently (not fully disambiguated, but the fix below addresses both).
- **Fix**: redesigned `host_software/src/touch_logger.py`'s `TouchTelemetryLogger` so its single worker thread owns *all* serial I/O -- both directions. The main thread (`main_onnx_shared_vision_audio.py`) no longer calls `ser.write()`/`ser.read()` at all; it only calls `send_frame(seq, x, y, target_x, target_y)` (registers the pending frame for echo-joining and enqueues the outgoing bytes) or `send_raw(b"L\n")` (lost-ball marker), both just pushing onto a `queue.Queue` -- no serial access, no lock needed for the hand-off. The worker thread drains the outgoing queue before each read attempt, so writes are never delayed behind more than one read-timeout window. CSV persistence is now an independent, optional feature of the same object (`csv_path=None` runs the thread purely for its I/O-consolidation benefit, with `--log-csv off` no longer meaning "the thread doesn't exist," just "it doesn't write rows") -- previously CSV logging and single-thread serial ownership were the same on/off switch, which was never the actual intent.
- **Complementary firmware change**: `TouchProbe.cpp`'s `TOUCH_RATE_HZ` lowered 60 -> 25, since 60Hz was producing several duplicate echo records per distinct vision frame once the host's real throughput was known to be ~20-25 FPS -- pure wasted read/parse volume on the host side for no benefit. Still comfortably above Nyquist for the ~1-5Hz oscillation frequencies actually relevant to the diagnostic.
- **Verified**: an isolated smoke test against a mock serial object (`send_frame`/`send_raw` correctly enqueue and get written by the worker thread, incoming echoes correctly join back to their pending frame, CSV persistence correctly toggles on/off independent of the thread's existence) -- both passed. Real hardware re-test (does control survive with `--log-csv` on now) still pending, not yet run on the physical rig.

### Live-Deployment Jitter Diagnosis: `main_onnx_shared_vision_audio.py`
- **Symptom**: on real hardware (STM32 RL control build, `firmware/stm32_ml_control_and_vision/`), the ball would reach center and hold for 2-5s, then drift again in a non-periodic, "random" (not oscillatory) way. Toggling `--mlp` made no visible difference, and the debug tracking dot looked visibly jittery in all configurations.
- **Root cause, found by tracing the actual code path (not assumed)**: `PredictionGate._handle_tracking()` (copied unchanged from `main_onnx_aruco_audio.py`) computed `self._ema` on every accepted frame but only used it internally for the *next* frame's jump-distance check -- the accept branch returned the raw `candidate` itself, and `_hold()` returned `self._last_good` (also raw). So the gate only ever filtered out large single-frame outliers; every value that passed (the large majority of frames) was relayed completely unfiltered, MLP-corrected or not -- explaining why `--mlp` toggling was invisible (the debug dot is drawn from `px_x/px_y`, computed immediately after the raw CNN forward pass, upstream of the gate and the MLP entirely).
- **Why this hits harder on the current firmware than it might have historically**: the currently-active RL control build has no position-side filtering of its own -- it EMA-filters *velocity* (finite difference of raw position, alpha=0.35) but consumes raw `ball x, y` and `error to target` directly in its 9-element observation. Differentiation amplifies high-frequency noise before the velocity filter ever sees it, and the position terms get no filtering at all. This is unlike the older PID/data-collection build (`firmware/BallBalancingBot/`), which had an EWMA settling filter, slew-rate limiter, and derivative-on-measurement specifically built to handle a noisy position sensor (the original resistive touchscreen) -- see 20/07/2026 and 10/07/2026 entries. None of that infrastructure carried over to the RL build's serial-fed vision input path. A neural policy also doesn't have a PID's clean periodic-oscillation failure mode when fed noise outside its training distribution, which plausibly explains why the drift looked "random" rather than patterned like earlier PID-era testing.
- **Fix**: `PredictionGate` now returns `self._ema` (the smoothed value) instead of the raw candidate on every return path (`_handle_tracking()`'s accept branch and `_hold()`), while `_last_good` still anchors the jump-gate's own accept/reject comparison to the true last-observed raw point (unchanged). The RL network's weights are fixed (`weights_best_so_far1.h`), so retraining wasn't an option here -- this smooths the signal before transmission instead, using the existing `--gate-ema-alpha` (no new CLI flag). Explicitly a live A/B experiment at the user's request ("we will revert back if it makes it worse"), not yet confirmed to fix the drift on hardware.

### Heatmap Target dtype Bug (Double vs Float) — Found via First Real Colab Run
- **Symptom**: first actual GPU training attempt on the shipped architecture crashed at `scaler.scale(loss).backward()` with `RuntimeError: Found dtype Double but expected Float`. Did not reproduce locally during the earlier smoke test (CPU-only machine, and `torch.cuda.amp.autocast(enabled=device.type=="cuda")` is a no-op on CPU, which tolerated the mixed dtype that GPU autocast/`GradScaler` strictly reject).
- **Root cause**: `SharedVisionDataset._make_multi_peak_heatmap()` (2026-08-12 heatmap-degeneracy fix) unpacked `cx, cy = centroids[label]` from `cv2.connectedComponentsWithStats()`, whose `centroids` output is always `float64`. Subtracting a `numpy.float64` scalar (not a plain Python `float`) from the `float32` coordinate grid in `_make_gaussian_heatmap()` triggers numpy's type-promotion rules, silently upcasting the whole Gaussian computation -- and therefore `heatmap_target` -- to `float64` for any frame with at least one visible marker.
- **Fix**: cast `centroids[label]`'s components to plain Python `float` before use (avoids the numpy-scalar promotion), plus explicit `.astype(np.float32)` on both `_make_gaussian_heatmap()`'s return value and the final combined array as defence in depth. Verified directly: `SharedVisionDataset[...]` now returns `heatmap_target` as `torch.float32` for a real multi-marker frame (previously would have been `float64`).
- **Scope check**: the overnight decoder trial (13/08 entries above) also uses `SharedVisionDataset` and was therefore also affected -- but all 30 of those runs used `device="cpu"` (confirmed by each run's own `Device: cpu` printout), so the same CPU/autocast tolerance that hid this bug in the local smoke test also means the trial's `ball_px_error`/`mask_iou` results (which don't depend on heatmap dtype) are unaffected; `heatmap_mse` values may have been computed at accidentally-higher float64 precision, a numerically negligible difference, not a validity issue. No re-run needed.
- **Not yet verified on actual GPU hardware** -- this machine has no CUDA device, so the fix is confirmed at the root-cause/dtype level but not by reproducing the original crash-and-recovery on GPU. Next Colab run is the real test.

### Decoder Trial: ConvTranspose2d vs. Upsample+Conv2d (FPGA hls4ml Layer Decision)
- **Motivation**: `ConvTranspose2d` (current `mask_head`/`heatmap_head` decoder) requires a custom hls4ml layer for FPGA deployment (`ml_system_parameter_budget.md` §5.9 step 3); `Upsample`+`Conv2d` uses two natively-supported hls4ml layers. - **Run 1 (3 seeds, production loss weights) was misleading**: showed `upsample_conv` with ~4x higher ball-tracking variance than `transpose` (std 9.6px vs 2.3px), driven entirely by one seed. Read initially as a real architectural instability risk to the ball-tracking control signal.
- **Run 2 (5 seeds, same weights) overturned that reading**: ball-error std became statistically indistinguishable between decoders (7.3px vs 7.3px) — the apparent instability was small-sample noise, not a `upsample_conv`-specific failure mode. Same lesson the 11/08 augmentation trial already taught this project (`ANALYSIS_2026-08-11.md`): don't trust a 3-seed ranking. - **Net reading**: the original case for keeping `ConvTranspose2d` specifically to protect ball-tracking stability doesn't hold up -- both decoders benefit equally from loss reweighting, and once that's controlled for, `upsample_conv` costs nothing on ball tracking while keeping most of its mask-quality advantage. Remaining real cost: +42% params (91,140 vs 64,260, both comfortably inside the 612.5KB BRAM budget). Full numbers: `host_software/ml_vision/experiments/results/ANALYSIS_2026-08-13.md`. - **OV7670 Resolution & VDMA Early Errors**: Diagnosed why the AXI VDMA engine was throwing `0x4000` (Error Interrupts) and hanging with `SOF Early` and `EOL Early` errors (Raw Status `0x00014191`). ## 21/07/2026
### Hardware Migration: Opal Kelly XEM3010 to ZedBoard (Zynq-7000)
- **Fatal Clocking Limitation**: Discovered a critical limitation with the Opal Kelly XEM3010 expansion header breakout board. The external `PCLK` from the OV7670 camera must be routed to a dedicated Global Clock (GCLK) input on the FPGA to maintain setup/hold times and signal integrity. However, the XEM3010 routes all available GCLK pins to its on-board Cypress PLL outputs, leaving zero GCLK inputs accessible on the user breakout headers. This forced ISE to route the 24MHz pixel clock through standard logic fabric, causing catastrophic clock skew, unpredictable metastability, and preventing reliable image capture.

## 17/07/2026
### FPGA Camera Breakthroughs (XCLK & SDRAM) — First Non-Black Frame Achieved
- **XCLK Architectural Routing Fix**: Discovered why the camera was receiving no stable clock regardless of PLL settings. The design used `assign xclk = clk2;` where `clk2` (pin P9) is a dedicated GCLK input routed through a BUFG by ISE. Xilinx Spartan-3 silicon rules forbid BUFG-driven nets from directly driving output pins — the router silently left pin K5 completely undriven (floating antenna, reading as 60–120mV noise on the DSO). The fix removes `clk2` from the design entirely.
- **Spartan-3 Primitive Limitation**: Initial fix attempted `DCM_SP` + `ODDR2` to generate 24MHz internally and forward it via a DDR output register. ISE reported `NGDBuild:604` — these primitives are Spartan-3E/3A only. The XC3S1000 (basic Spartan-3) does not support them.
- **Counter-Based XCLK (Final Solution)**: Replaced with a 2-bit counter driven by `clk1` (100MHz SDRAM clock). `assign xclk = xclk_cnt[1]` produces a 25MHz, 50% duty-cycle clock from a normal fabric flip-flop, which ISE legally routes to pin K5 without restriction. OV7670 XCLK spec is 10–48MHz; 25MHz is within range.
- **SDRAM Controller INIT/REFRESH Collision**: Identified the root cause of the persistent black frames. The `sdram_controller.v` `busy` signal was only asserted during `READ`/`WRITE` states — not during `INIT` or `REFRESH` cycles. The arbiter therefore issued write commands during these forbidden windows, which the controller silently dropped. Fixed by asserting `busy` on all non-IDLE states (`busy <= (next != IDLE)`).
- **First Non-Black Frame**: After a power cycle and flashing the new bitstream, `grab_frame.py` successfully captured 5 frames back-to-back. `check_status.py` confirmed all counters (`PCLK`, `HREF`, `VSYNC`) are alive. `test_frame.png` shows full-frame noisy/garbled content (magenta banding) — **not black** — confirming the camera is alive and producing real pixel data for the first time on the FPGA path.
- **Remaining XCLK Signal Integrity**: DSO on pin K5 (JP3-41) shows max 1.88V (expected 3.3V LVCMOS33) and ~120mV amplitude at variable frequency. This is consistent with weak I/O drive strength or capacitive loading on the wire. Subsequent runs without a power cycle show intermittent frame timeouts and frozen PCLK counters, directly correlated with the unstable XCLK. Image corruption (garbled pixels, horizontal banding) is also consistent with XCLK instability causing the OV7670 to lose pixel sync.

- **Camera Blackout & Clock Domain Synchronization**: Diagnosed an issue where `camera_top.v` would lock up completely after reading a single frame. - **Clock Generator VCO Range Bug**: Discovered that the CY22393 PLL was completely failing to lock on the 24MHz `xclk` because the Python configuration requested a VCO frequency of 48MHz (which violates the strict 100-400MHz operational bounds of the chip). Recalculated the PLL multipliers in `grab_frame.py` to use a 240MHz VCO divided by 10, perfectly resolving the instability.
- **Asynchronous FIFO Reset CDC Bug**: Diagnosed a major cross-clock domain hazard where the host's asynchronous `reset` signal was driving the synchronous `rst_n` pin of the 100MHz SDRAM state machine. Implemented a dual-rank flip-flop CDC synchronizer in `sdram_arbiter.v` to safely buffer the reset signal into the 100MHz domain, eliminating metastability lockups.
- **OV7670 PWDN Shutdown Cascade**: Uncovered a massive, cascading pipeline failure that caused the Python `ReadFromBlockPipeOut` loop to hang forever. Discovered that the FPGA `v_sup` pin (mapped to the camera's active-high Power Down `PWDN` pin) was hardcoded to `1'b1`. This actively commanded the camera to enter deep sleep immediately upon startup. The camera would output exactly 23,172 clocks (~1 millisecond) before completely dying, meaning it never emitted a single `VSYNC` or `HREF`, which kept the SDRAM arbiter starved and locked up the USB FIFO pipeline. Fixed by setting `v_sup = 1'b0` to wake the camera.

- **YOLO Flipping Bug**: Discovered a critical issue where default YOLOv8 augmentations (`fliplr=0.5`) were silently corrupting our dataset. Because our keypoints had strict spatial semantics (e.g., Keypoint 0 = Top-Left), horizontal flips essentially mirrored the image without mirroring the semantic labels, severely penalizing the model during training. Explicitly disabled `fliplr=0.0` and `flipud=0.0` in `train_yolo.py`.
- **CAD Plate vs. Resistive Touchpad Dimensions**: Solved an elusive homography projection bug that was "shrinking" our targets and ball mapping inward. Reconciled the fact that the 4 YOLO-Pose keypoints visually track the outer boundaries of the purple acrylic plate (`200.0 x 146.93 mm`), while the telemetry data (`touch_x`, `touch_y`) and target coordinates strictly exist within the inner resistive touchpad (`187.5 x 142.0 mm`).

Shifted the internal Target coordinates into this Plate Space by adding half the difference (`PAD_OFFSET_X`, `PAD_OFFSET_Y`) and properly mapping the ball by adding half the Plate dimensions. This flawlessly aligned the telemetry with the visual bounding box.
- **360-Degree Rotation Invariance**: Realized that restricting YOLO to a single viewing angle was limiting. Rewrote the dataset generation pipeline to apply random arbitrary rotations (0 to 360 degrees) to the raw 02_silver dataset images.
- **Physical Keypoint Anchoring**: To ensure the semantic meaning of the keypoints survived 360-degree rotations, we physically anchored Keypoint 0 to the corner anti-clockwise from the motor lip. By applying OpenCV's affine rotation matrix to both the image pixels and the 4 physical keypoint coordinates simultaneously, the model is trained to track the physical geometry of the board regardless of the camera's orientation.
- **Movable Target Detection (YOLO)**: Reconciled that the 4 colored control targets (Green, Red, Black, Grey) are not fixed corners, but rather physically movable markers placed anywhere on the board for the ball to balance towards. Because they are trained as independent object classes (not rigid pose keypoints), the trained YOLO model will successfully track them even when they are moved to new locations in the real world.
- **Intrinsic Coordinate Invariance (ResNet)**: We originally thought applying PyTorch `RandomAffine` or `RandomPerspective` to the ResNet Expert Tracker without modifying the target labels was a bug. However, we realized that the labels (`touch_x`, `touch_y`) are *intrinsic* to the physical board! If the camera translates, zooms, or rotates (extrinsic changes), the physical position of the ball on the board NEVER changes. Therefore, applying these geometric augmentations *while keeping the labels identical* is mathematically perfect! It brilliantly forces the CNN to learn camera-invariance by locating the purple shape of the platform's outline to calculate relative position, rather than memorizing absolute pixel locations.
- **The Only Forbidden Augmentation**: `RandomHorizontalFlip` remains strictly forbidden for both models. Flipping the image mirrors the board (e.g. swapping the left/right targets), creating a physically impossible hardware layout that destroys the intrinsic coordinate system.

## Spatial Softmax Geometric Scaling Bug (July 30, 2026)
- **Issue:** The arbitrary MAX_BOUND = 200.0 constant used across all datasets and evaluation scripts correctly functioned as a symmetric scaler for the old Dense-layer models, but catastrophically broke the new Spatial Softmax models.
- **Root Cause:** Dense layers are mathematically agnostic to geometric constraints and simply memorized the scaled value (e.g. 0.468). However, Spatial Softmax maps the absolute edge of the warped camera image to precisely 1.0. By dividing the 93.75mm physical plate edge by 200.0, the target label was artificially compressed to 0.468. This forced the Softmax to predict the ball was near the center of the image when it was physically at the extreme edge, resulting in a training paradox.
- **Resolution:** Replaced the arbitrary 200.0 constant system-wide with decoupled, physically accurate bounds corresponding to the Homography-warped plate edges (MAX_X_BOUND = 93.75, MAX_Y_BOUND = 71.0). Note that this obsoletes all previous Dense-layer model checkpoints.
