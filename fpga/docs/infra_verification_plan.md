# FPGA Surrounding-Infrastructure: Audit & Fix/Verify Plan

**Owner:** `agent_fpga` (this agent's own scratch-to-ground-truth planning doc; not yet human-reviewed).
**Scope:** Domains 1, 3, and 4 of `.agents/agent_fpga.md` — the OV7670→VDMA→UDP camera/video pipeline, the PID+IK HLS control core and its integration into the live PS application, and repo hygiene. **Explicitly excludes Domain 2** (vision-model weight compilation, `fpga/hls4ml_custom_layers/`, GELU LUT, quantization trials) — that is the ML-deployment agent's active work; this plan does not read for changes there beyond what's already documented in `.agents/agent_fpga.md`, and makes no changes under `fpga/hls4ml_custom_layers/`.

## 1. Current-state audit (concrete findings, file-referenced)

### 1.1 Camera → VDMA → UDP pipeline: three divergent, uncoordinated implementations

- **`fpga/vitis/src/main.c`** — the app CMake actually builds (`udp_camera_app` per `CMakeLists.txt`). Port 8080, 640×480 RGB565. `init_vdma()` is commented out (`main.c:163`), so it currently streams whatever raw bytes sit at `0x10000000` in DDR — **not real camera frames** — this is the documented "ping-test" state, confirmed still true. Calls `Xil_ExceptionEnable()` directly, not `platform_enable_interrupts()`.
- **`fpga/vitis/src/udp_camera_stream.c`** — a second, different `main()` in the *same source directory*. Port 5001, 640×480, VDMA enabled with frame-counter-interrupt polling. Because `CMakeLists.txt` does `aux_source_directory(${CMAKE_CURRENT_SOURCE_DIR} current_dir_sources)`, **both files are pulled into the same build**, which is a duplicate-`main()` link error waiting to happen (or already happening) — need to confirm which file is meant to be live and remove/relocate the other.
- **`fpga/zedboard_files/main.c` + `udp_rx_viewer.py`** — an older/third generation: uses `XAxiDma` simple-mode (not VDMA), port 5005, packs pixels as 12-bit RGB444 in 16-bit fields, one UDP packet per video row with **no** frame/packet header (a different wire protocol than the other two, which use a `PacketHeader{frame_id, packet_id}`). Ships its own `.xsa` hardware handoff file — likely a separate, earlier Vivado build, not `zynq_camera_sys/`.
- **Resolution regression vs. documented ground truth.** `docs/PROJECT_LOGBOOK.md`'s 23/07/2026 entry ("QVGA Fix") states the team deliberately dropped 640×480 for 320×240, because 640×480 RGB565 @30fps (~147.4 Mbps) exceeds the ZedBoard's realized 100 Mbps link and was causing VDMA errors — "We updated the C VDMA configuration and the Python UDP receiver script to natively expect 320x240." **None of the current sources reflect that**: `main.c`, `udp_camera_stream.c`, `zedboard_files/main.c`, `host_software/tools/receive_udp_video.py`, and `fpga/zedboard_files/udp_rx_viewer.py` all hardcode 640×480. Worse, **`fpga/camera_i2c/ov7670_axi_stream.v`** — the RTL wrapper actually instantiated in the live `zynq_camera_sys` Vivado block design (confirmed via the `camera_system_ov7670_axi_stream_0_0` IP instance under `fpga/zynq_camera_sys/.../bd/camera_system/ip/`) — hardcodes AXI-Stream `TLAST` at exactly 640 pixels/row (`ov7670_axi_stream.v:76`), i.e. VGA framing, not QVGA. Either the QVGA decision was reverted without updating the logbook, or the fix never made it into this RTL file. **Needs EE confirmation before any further camera work** — this single fact (640 vs 320) cascades into RTL framing, VDMA buffer sizing, C, and the Python receiver.
- **Documented UDP interrupt fix appears unapplied, and may not even apply to the current toolchain flow.** `docs/udp_troubleshooting_findings.md` root-causes earlier "Request timed out" ping failures to a missing GIC master-handler registration, fixed by calling `platform_enable_interrupts()` instead of raw `Xil_ExceptionEnable()`. But:
  - Neither `main.c` nor `udp_camera_stream.c` calls `platform_enable_interrupts()` today — both still call `Xil_ExceptionEnable()` directly.
  - The function that implements the documented fix, `platform_zynq.c:platform_enable_interrupts()` (line 244), only compiles when `SDT` is **not** defined (`#ifndef SDT`, `platform_zynq.c:49`). This project's `platform.c`, which compiles under `#if defined(SDT) || ...` (`platform.c:29`), **never defines `platform_enable_interrupts()`** even though `platform.h:57` declares it unconditionally. `docs/udp_research_guide.md` discusses "Vitis SDT" explicitly, and `platform.c`'s SDT branch uses `xiltimer.h`/`xinterrupt_wrap.h` (the modern SDT interrupt-wrapper API) — consistent with this project actually building under the SDT flow. If so, calling `platform_enable_interrupts()` from `main.c` today would be a **link error**, and the documented fix (written for/tested against the classic non-SDT BSP) may not transfer as-is. This is a real build-and-see question, not something to guess from memory — flagging per the hard rule on Vitis 2025.2 uncertainty.
- **Minor:** `main.c` redefines `PC_IP_1..4`/`PC_UDP_PORT` twice with identical values (`main.c:17-21` and `44-49` — harmless, just sloppy); and has `#include "xil_exception.h"` inside the body of `main()` (`main.c:157`) — legal C, but worth cleaning up.

### 1.2 PID + IK HLS core: IK geometry is correct, but the control law is a stale, simplified snapshot

- **IK geometry matches exactly.** `fpga/hls_hardware/InverseKinematics.cpp` (`d=86.2, e=50.0, f=87.0`) is bit-for-bit the same geometry as `firmware/BallBalancingBot/InverseKinematics.cpp` (the STM32 single source of truth per `AGENTS.md`), just ported to `ap_fixed<32,16>`. The algorithm itself needs no changes — good foundation.
- **The PID law is not the current tuned control law.** Concrete mismatches, `fpga/hls_hardware/PIDControllers.cpp` vs. `firmware/BallBalancingBot/PIDControllers.cpp`:
  - **Gains:** HLS uses `kp=0.8, ki=0.2, kd=0.09` (`PIDControllers.cpp:4-6`) — these are literally the *pre-tuning* values, now left as commented-out historical markers in the STM32 source (`#define kp 0.25 //.8` etc.). The STM32's live gains are `kp=0.25, ki=0.1, kd=0.06`, plus an entirely separate near-setpoint gain set (`kp_adj=0.3, ki_adj=0.3, kd_adj=0.05`, engaged when `|error|<25mm`) that the HLS core doesn't implement at all.
  - **Loop rate:** HLS assumes a fixed `dt=0.001` (1kHz, `PIDControllers.cpp:13`); the STM32 runs at ~30Hz with a *measured* variable `dt`, and its derivative filter constant (0.35) and integral clamp (±50) are calibrated for that ~30Hz cadence. Porting the STM32 gains verbatim to a 1kHz loop without re-deriving the dt-dependent terms would not reproduce the same closed-loop behavior.
  - **Missing behaviors entirely:** derivative-on-measurement low-pass filtering, the predictive-velocity term (`kv`, currently zeroed on the STM32 but present as scaffolding), setpoint slew-rate limiting (80mm/s), edge/"virtual wall" protection, integral reset after 3s of no ball detected, and the correct output clamp (STM32 now uses `max_output=73.5`; HLS still has the old `83.5`, `PIDControllers.cpp:9`).
  - **Platform height mismatch:** HLS hardcodes `h=120.0` when calling `get_angles()` (`PIDControllers.cpp:70`). The STM32's balancing call is `move_to_angle(output_angles[0], -output_angles[1], 80)` — i.e., **h=80** during live balancing (`BallBalancingBot.ino` → `MotorControl.cpp`; note `h0=87` in `MotorControl.cpp` is a *different* constant, the height at motor-zero/homing, not the balance height). A 120 vs. 80mm difference is a ~50% geometry error and would very likely produce visibly wrong tilt angles on real hardware. This looks like a bug, but since it's a physical-hardware calibration constant, **needs EE confirmation, not a silent fix**.
  - **Sign/argument convention is correct as-is:** HLS's `get_angles(angle_y, -angle_x, h)` matches the STM32's `move_to_angle(output_angles[0]/*Y*/, -output_angles[1]/*X*/, h)` — no change needed there.
- **Not wired at all.** `fpga/vitis/src/main.c` never calls `balance_controller()` — today it only does camera/UDP work. There's no AXI-Lite driver stub, no coordinate-input path (from host PC or a future on-board CNN), and no motor-output path in the PS application yet.
- **No motor/stepper driver exists on the FPGA side.** `fpga/hls_hardware/` only produces target angles (`thetaA/B/C`), analogous to the STM32's `get_angles()`. The STM32's `MotorControl.cpp` (step conversion, `AccelStepper` accel/speed profiles, homing sequence, proportional-speed smoothing via `speed_controller()`) has **no FPGA equivalent yet** — this is a full open subsystem, not a two-function wiring job.

## 2. Ordered fix/verify plan

### Phase 0 — Blocking questions for the EE (cannot safely proceed past Phase 1 without these)
- **Q1:** VGA (640×480) or QVGA (320×240)? Determines RTL `TLAST` framing, VDMA buffer sizing, and every C/Python endpoint.
- **Q2:** Which of `main.c` / `udp_camera_stream.c` / `zedboard_files/main.c` is canonical? Confirm `zynq_camera_sys` is the live Vivado project (vs. whatever produced `zedboard_files/ov7670_eth_xsa_file.xsa`).
- **Q3:** Is this project actually building with `SDT` defined? Determines which `platform_*.c` is live and whether `platform_enable_interrupts()` exists to link against.
- **Q4:** Balance height `h=80` or `h=120` — which is physically correct for the current platform build?

### Phase 1 — Camera/UDP pipeline cleanup and fix (Domain 1)
1. Once Q1-Q3 are answered: keep exactly one `main()` under `fpga/vitis/src/`; move the other implementation(s) out (e.g. to a clearly-labeled reference location) so the build isn't ambiguous.
2. Resolve the interrupt-registration question for real — either confirm `platform_enable_interrupts()` is reachable and correct under this project's actual SDT/non-SDT configuration, or determine the SDT-flow's correct equivalent, and add a short dated note under `fpga/docs/` explaining how/why it differs from `udp_troubleshooting_findings.md`'s classic-BSP fix (that doc stays as historical record, not silently edited).
3. Re-enable VDMA (`init_vdma()`) in the chosen `main.c`; align `WIDTH`/`HEIGHT` with the Phase-0 answer, and make sure the RTL framing (`ov7670_axi_stream.v`), the VDMA buffer size, and the Python receiver all agree on the same resolution.
4. Verify in order (per `AGENTS.md`'s FPGA verification sequence): (a) raw camera sanity check if a VGA monitor is available, (b) single-frame capture routed to the host PC for pixel-level inspection, (c) sustained UDP stream FPS/drop-rate measurement against the corrected Python receiver.

### Phase 2 — PID/IK control-law parity and integration (Domain 3)
1. Before wiring anything: bring `fpga/hls_hardware/PIDControllers.cpp/.h` up to parity with the current STM32 tuned law — dual near/far gain sets, dt handling appropriate to whatever loop rate the FPGA will actually run at (this needs an EE decision on target HLS loop rate — 1kHz vs. ~30Hz isn't just relabeling `dt`, the tuning itself is rate-dependent), derivative filtering, slew-rate limiting, edge protection, integral-reset-on-no-detection, and the corrected output clamp and height constant (once Q4 is answered).
2. Write an HLS C-simulation testbench *before* touching synthesis or hardware: feed known `(current_x, current_y, setpoint_x, setpoint_y)` tuples through `balance_controller()` and diff `thetaA/B/C` against the STM32's `get_angles()` computed offline for the same inputs, to catch fixed-point precision or logic-porting bugs early.
3. Decide the actual PL/PS integration point with the EE (a real Vitis/HLS-IP question I shouldn't guess): is `balance_controller` meant to be an AXI-Lite-controlled PL IP core invoked from the PS loop (which is what the current `s_axilite` pragmas assume), or should the control law just run as PS software? Nothing currently instantiates it in the block design either way.
4. Scope boundary: this phase only produces target motor angles. Actual stepper-motor driving (step/dir generation, accel/speed profiles, homing) doesn't exist on the FPGA side yet and should be its own follow-up plan once Phase 2 lands — not silently bundled in here.

### Phase 3 — Repo hygiene (Domain 4, ongoing/low priority)
- Flag (not fix) the stale Opal Kelly reference in `hls_hardware/TODO.md` and the doc duplication under `fpga/`.
- Once Phase 0/1 confirms the canonical camera pipeline, propose — don't unilaterally execute — archiving `fpga/zedboard_files/` and the duplicated root-level docs.

## 2.5 Addendum (2026-08-13, post EE conversation) — answers/new findings on the "surrounding infrastructure" questions

Answers received on the broader integration questions I raised beyond Phase 0 (ArUco-warp location, PL/PS dataflow split, agent division-of-labor, bring-up contract, motor driver, timing budget, HLS testbench environment):

- **Warp location (A):** There are separate deployment prototypes — a "digital laptop version" and an FPGA deployment of `ml_vision` — implying the warp may not need to be replicated on-chip in this phase if the laptop path stays the bring-up path. **Still incomplete** — need the rest of this answer (which prototype is the near-term target) before this actually resolves anything.
- **PL vs. PS dataflow split (B):** Open, needs research — not decided yet. Not blocking Phase 1/2 work below.
- **Division of labor at the ML-agent integration seam (C):** Explicitly routed to the orchestrator (`agent_main`) to resolve, not mine to decide unilaterally. Not resolving this myself.
- **Bring-up coordinate contract (D):** The vision side will append an MLP to the CNN head that outputs the ball's `(x_mm, y_mm)` directly. **Flag:** this appears to contradict `AGENTS.md`'s LOCKED architecture decision "Coordinate mapping: ArUco homography → warped → pixel × scale = mm (**no MLP**)". Not mine to silently reconcile (I don't own `AGENTS.md` or the vision model) — surfacing it, not fixing it. Regardless of which coordinate-production method wins, the FPGA-side contract only needs to accept a numeric `(x_mm, y_mm)` pair, so this doesn't block Phase 2's integration design. **Concrete precedent found:** `firmware/stm32_ml_control_and_vision/BallBalancingBot/SerialCoords.cpp` already defines exactly this kind of bring-up contract for the STM32 — a simple ASCII line protocol over serial (`"<x_mm>,<y_mm>[,<target_x>,<target_y>[,<z>]]"`, `L`/`N` for "lost", 150ms staleness timeout, clamped to the physical plate). Recommend the FPGA bring-up contract mirror this format verbatim (same field order/units/sentinels), just carried over UDP instead of UART, so host-PC tooling and mental model transfer directly. Proposing this concretely in Phase 2 rather than inventing a new format.
- **Motor driver (E):** Confirmed — it already exists. `fpga/main_controller/stepper_motor_controller.v` is a synthesizable step/dir pulse generator (accumulator-based proportional speed control from `target_position - current_position` error) with **no** Opal-Kelly-specific I/O in the module itself (pure `clk/rst/target_position → step_pin/dir_pin/current_position`) — unlike the rest of `main_controller/`, this file looks portable to Zynq PL with a new clock source and a fresh XDC pin mapping (none exists yet for motors, unlike `camera_pinout_zedboard.md`). **Caveat found:** its speed cap is hardcoded to ~700 accumulator units (~2 kHz max step rate, per its own comment), while the STM32 reference (`MotorControl.cpp:motor_init()`) runs `setMaxSpeed(6000)` — 3× faster. Reusing this module means either re-deriving the speed/accel constants for the real TMC2208 step-rate ceiling, or accepting a slower FPGA motor response than the STM32 currently achieves — needs an EE decision, not a guess. (`fpga/tests/motor_test/motor_test_top.v` also exists but is Opal-Kelly FrontPanel-specific — a single-motor step-rate bench test, not reusable RTL, just historical confirmation the step/dir wiring was bench-validated at some point.)
- **Timing budget (F):** Read `firmware/stm32_ml_control_and_vision/BallBalancingBot/` (the RL-control variant, architecturally the closest existing analogue to "vision + control combined on one board"). Key structural finding, not just a number: **vision and control are two independently-paced loops glued by a "last known coordinate + fresh flag," not one monolithic per-frame pipeline.**
  - `RLControl.cpp`'s `CONTROL_DT = 0.0333f` (30 Hz) is the cadence the control network was *trained* at — both the RL policy and (per the earlier PID-core comparison) the tuned PID gains are calibrated around ~30 Hz, i.e. camera frame rate, **not** a fast fixed-timer rate. This directly answers my earlier "1 kHz vs ~30 Hz" open question from Phase 2: the correct target loop rate for the control-law evaluation is ~30 Hz (frame-synchronized), not 1 kHz.
  - `SerialCoords.cpp`'s `coords_available()` decouples "a new vision sample arrived" from "run a control step" — vision publishes whenever a frame is processed, `rl_balance()`/`pid_balance()` only recompute a new target when a fresh coordinate lands (or a 100ms/500ms timeout fires).
  - Motor **stepping** itself (`motorX.run()`) is called every loop iteration "as fast as possible," fully decoupled from the ~30 Hz control-law cadence — this is exactly the two-tier structure `stepper_motor_controller.v` already assumes (continuous fast pulse generation driven by a `target_position` register that updates only occasionally).
  - **Implication for the FPGA design:** the PID/IK HLS core should be invoked once per incoming vision coordinate (~30 Hz, frame-synchronized) rather than on a fast fixed clock; the stepper pulse generator should run continuously/independently at its own (much higher) rate off the last-written target-angle register. This resolves the "loop rate" blocker in Phase 2 step 1 above — plan to build it this way unless corrected.
- **HLS testbench environment (G):** Still open — more info needed, not yet available.
