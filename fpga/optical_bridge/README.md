# `fpga/optical_bridge/` — PRELIMINARY / SPECULATIVE sketch only

**Read this before reading any file in this directory as a design.** This directory is
scaffolding written ahead of a decision nobody has made yet. It exists so that when the real
decision lands, there is a concrete skeleton to edit — not because the shape below has been
reviewed, approved, or even fully reasoned through for a real target.

## The blocker this sits on top of (STILL OPEN, unchanged as of 2026-10-14)

`fpga/docs/optical_bridge_interface_spec_draft.md` is the actual spec-drafting work for this
bridge (Arm 3 of the 3-arm VLA comparison). Its §1 asks the one question everything else here
depends on, and that question has **not** been answered by the user/PI:

> Is Arm 3 (a) a real fabricated photonic chip this project has or will have physical/electrical
> access to, (b) a simulation/co-design-only stand-in with no real analog hardware at all, or
> (c) a commercial photonic accelerator product (i.e. "read the vendor's datasheet," not design
> an interface)?

The spec draft's own recommendation is: **"don't proceed to any RTL/HLS or AXI4-Lite
register-map design for this bridge until question 1 has a real answer."** This directory does
exactly that anyway, but only as a drafting convenience under framing (a) — same choice the spec
draft itself made in its own §1, for the same reason (it's the only scenario with any concrete
numbers to sketch against). **Nothing in this directory is a step toward committing to (a)
over (b)/(c).** If the answer turns out to be (b) or (c), most of what's in this directory
(the AXI4-Lite DAC/ADC register file, the placeholder parallel bus, the write-then-read FSM
shape) is very likely the wrong shape entirely, not a design to extend.

Do not let this code's existence be read by anyone (including a future session of this same
agent) as evidence that the framing question got resolved. It didn't.

## What's in here

- `optical_bridge_axi_lite.v` — a behavioral Verilog sketch of an AXI4-Lite register
  wrapper around a calibration-table store (`2N-1` DAC write entries + `C` ADC read entries,
  per the spec draft §3.1/§4) and a simple write-then-read sequencing FSM (write all DAC
  entries out → wait a placeholder settle period → read all ADC entries in). It follows the
  same AXI4-Lite packaging convention already used for `fpga/camera_i2c/ov7670_axi_stream.v`
  (→ `fpga/zynq_camera_sys/camera_system.bd`) and planned for the in-progress Domain 4 port of
  `fpga/main_controller/stepper_motor_controller.v`. **Not meant to synthesize against real
  silicon yet** — it has never been run through synthesis, has no real DAC/ADC bus underneath
  it (see below), and uses a made-up settling-time constant.
- `sim/tb_optical_bridge_axi_lite.v` — a self-checking, simulation-only testbench. No real
  DAC/ADC, no real board, no physical hardware anywhere in this directory.
- `sim/xsim.dir/` (generated by running the testbench — not checked in deliberately, see
  below) — Vivado xsim's working directory.

## Every placeholder, and what has to replace it before this is real

Every one of these is called out as `PLACEHOLDER` inline in `optical_bridge_axi_lite.v`'s
parameter list and body. Restated here as a checklist:

| Placeholder | Current value | What has to happen before it's real |
|---|---|---|
| `N` (input channel count) | 10 | Spec draft §1 answered as (a); then a real project device's actual channel count (§8 Q2) |
| `C` (output/readback channel count) | 10 | Same as above |
| `DAC_WIDTH` | 12 bits | Spec draft §3.2 only has a `DERIVED` ~11-bit estimate back-calculated from someone else's calibration sweep, not a real DAC spec — needs a real DAC part/datasheet |
| `ADC_WIDTH` | 12 bits | No ADC/photodetector part has been evaluated at all (spec draft §4, `UNKNOWN`) — this is an arbitrary symmetry guess, not even a derived number |
| `SETTLE_CYCLES_PLACEHOLDER` | 16 sim cycles | Spec draft §3.3 flags the real actuator settling time (thermo-optic or whatever EO/Pockels-class modulator eventually gets used) as a genuine, unquantified unknown — this constant is not connected to any real time unit at all right now |
| `ADC_LATENCY_CYCLES_PLACEHOLDER` | 4 sim cycles | Same — no real ADC/readback latency number exists anywhere in the source material |
| `dac_bus_*` / `adc_bus_*` ports | a generic parallel address/data/strobe bus, invented for this sketch | No real DAC/ADC bus protocol has been chosen. This is **not** SPI, **not** I2C, **not** any real part's interface — it's the minimum shape needed to demonstrate an FSM walking addresses, nothing more. Expect this to be replaced wholesale once a real part is picked. |
| AXI4-Lite register map (`ADDR_CTRL`/`ADDR_STATUS`/`ADDR_DAC_BASE`/`ADDR_ADC_BASE` offsets) | arbitrary word layout | `PROPOSED` pattern-matched from this project's existing AXI4-Lite packaging convention, not reviewed by anyone. A real register map should be designed against whatever the PS-side driver code and a real DAC/ADC part actually need, not kept as-is by inertia. |
| Serial, one-channel-at-a-time DAC write / ADC read sequencing | fully serial, 1 entry per cycle | A real bridge might need to write/read channels in parallel, or in a different order, or with per-channel settling rather than one bulk wait — this FSM shape is the simplest possible "write-then-read sequencing" skeleton the task asked for, not a claim about real timing feasibility (which is exactly the question the spec draft's §3.3/§8 Q4 leaves open) |
| `s_axi_wstrb` handling | ignored; full-word writes only assumed | A real AXI4-Lite slave should honor byte strobes; this sketch doesn't, which is fine for a register file this small in simulation but would need fixing for a general-purpose peripheral |

Also note: the module's `dac_bus_wr_en`/`adc_bus_rd_en` strobes pulse for exactly one clock
cycle and nothing downstream is modeled as having any real setup/hold requirement, bus
arbitration, or multi-driver contention — because there is no real bus to have those
properties yet.

## What this directory deliberately does not attempt

Same list as the spec draft's §6, restated here because it still applies:

- No synthesizable, board-verified RTL.
- No real DAC/ADC part number, bus protocol, or timing budget.
- No laser-source plan, no recalibration/drift-handling design.
- No claim about whether the 120Hz/8.3ms control-loop budget (`CLAUDE.md`) binds Arm 3 at all
  — spec draft §3.3/§8 Q5 leaves this open too.

## Simulation: how it was actually run, and the real result

This project's Vivado 2025.2 install (`C:\AMDDesignTools\2025.2\Vivado\bin`) provides the
`xvlog`/`xelab`/`xsim` toolchain; that's what was used here (no `iverilog`/`vvp` found on this
machine's PATH, despite `fpga/testbenches/camera_i2c/run_tests.sh` assuming it — flagging that
as a separate, pre-existing doc/tooling inconsistency, not something fixed in this session).

Commands run from `fpga/optical_bridge/sim/` (PowerShell, since the `.bat` wrappers need a
Windows cmd-style environment):

```powershell
& "C:\AMDDesignTools\2025.2\Vivado\bin\xvlog.bat" --sv "..\optical_bridge_axi_lite.v" "tb_optical_bridge_axi_lite.v"
& "C:\AMDDesignTools\2025.2\Vivado\bin\xelab.bat" tb_optical_bridge_axi_lite -s tb_sim
& "C:\AMDDesignTools\2025.2\Vivado\bin\xsim.bat" tb_sim -runall
```

**Real result (2026-10-14): all checks passed, 0 errors.** The testbench ran the
write-then-read sequence twice each against two parameter sets — the module's own small test
sizes (N=3, C=2) and its placeholder default sizes (N=10, C=10) — checking: the VERSION
sanity register, DAC-table write/readback over AXI4-Lite, BUSY/DONE status transitions, that
the placeholder `dac_bus`/`adc_bus` ports are strobed through every index exactly once in
order (monitored independently of the AXI side), and that ADC-table values latched during the
sequence match the placeholder test-harness's known address-derived values when read back.
Re-triggering the sequence a second time without a reset also passed, confirming the FSM
rearms correctly.

This confirms the sketch's own internal logic is self-consistent in simulation. It does
**not** confirm anything about real DAC/ADC/photonic hardware, real timing feasibility, or
anything else the placeholders table above lists as still unknown — there is nothing real on
the other side of this bridge to confirm against yet.

The `sim/xsim.dir/` working directory and `.wdb` waveform database are simulator-generated
build artifacts, not source — fine to delete/regenerate, not worth committing.
